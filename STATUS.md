# Current Development Status

## Current focus

**The six features to make Fragmentor sellable are built and merged**, decided on 2026-09-27 and planned in the git-ignored `scratch/plans/`, whose `PROGRAMME.md` keeps the order, the checkpoints and every decision made:

1. **First run on a real codebase.** Done, and judged by the person. Two rounds of trials — Claude agents following the guide on json-server, the realworld Express API and empty folders, scored from git and the check in `scratch/trials/findings.md` — and what they taught is in the guide and the check: contracts are type declarations, so a rebuild leaves the buyer's build as it was; the app's first minutes are Phase 2; a large system opens readable at 60%. Round two left no footprint and no broken build, and what it still found was folded in as the round-two fixes. The person then ran the real thing, Claude Code rebuilding json-server, and found one loose end: the agent left `.claude/skills/` uncommitted, though the rebuild command's own list names it. Noted for round three.
2. **Recorded traces.** Done. **Record** is on the execution bar: it runs the real code, lights the blocks and stores as it plays, and the recording reads as Tree or Flow behind a **Written down | Recorded** toggle. Each step written down says whether the recording saw it, a pill on the bar says where the two agree, and a contradicted step opens a note to the agent with the finding filled in. `fragmentor test` does the same for the agent, naming each step it could not check and why. Recordings live in memory only. Only code held to its contract is recorded: running code that is only drawn, in order to record it, was decided against for now on 2026-10-06, because it would run code as it stands, starting from nothing and able to reach the network, while runs captured from the person's own application would show the same thing truthfully (planned in `plans/real-runs.md`).
3. **Architecture rules and verified access.** Done. Code reaching a service, client, database or queue the diagram does not declare is a warning with Flag (one true warning each on the trial rebuilds, no false ones), and the person's own rules are made by clicking: select two blocks, **Add a rule…**, either "must never reach" or "only … may reach", with a reason. Rules live in `.fragmentor/rules.json`, written by the app and committed with the project; a definite break is an error that stops the agent's check, a guessed one warns; the agent may re-point a rule only when it moves the named block. A project with no rules shows no rules chrome at all.
4. **Changes.** Done. When the agent's work changes the architecture, a bar appears: "Since you last looked: N changed…". Clicking it lists the changes in words — new, built, moved with the evidence, changed, removed with **See it as it was** — puts a small dot on each changed block, and **Compare with then** runs both versions' tests. **Mark as seen** clears it; the bookmark stays in this computer's app profile, never in the project, and is only ever a real commit, so a restart cannot relist the whole project as new. No git, no bar; a repository with no commits yet is treated the same, with one sentence saying to ask the agent to commit.
5. **Python.** Done, to the same bar as TypeScript: contracts are plain typed dictionaries in an importable mirror, `blocks/_contracts/`, imported for types only; `fragmentor check` holds bound code to form rules run with the project's own interpreter and typechecks it with bundled pyright, against a config nothing in the project can weaken; and `harness.py` runs, watches, pauses and tests blocks over the same messages as the TypeScript harness, held to it by a parity test. The guide teaches the same worked example written in Python, proven by test to check clean, pass and record. The interpreter is the project's `.venv` first — one that will not do is reported, never passed over — then PATH, needing 3.11 or later, and the machine needs nothing else: pyright ships with Fragmentor.
6. **Export.** Done. **File › Export…** saves the open project as one read-only page that opens in any browser, drawn as the person arranged it — their colours, folds, dependencies and picked step — with the executions the agent wrote down to step through on the tree or as a Flow. It holds no code, notes, tests or folder paths, says how many problems there were without their messages, and makes no requests.

The work happens on `block-notes`, the trunk, each effort on a short-lived branch off it. `checkpoint/pre-programme` marks where it started.

What came before this is the redesign separating architecture from execution. The block tree means containment only; runtime behaviour is in executions: a trigger, the conditions it happens under, and the trace of everything that followed. `PROJECT.md` describes the model. Its phases:

1. **Done: the trace kernel, on its own.** `src/model/trace.ts` holds addresses, the three kinds of event (interaction, return, effect), entered and activated, `place`/`placeEvent`, which say where an event is drawn given how much of the architecture is showing, `travelOf`, which says which way a step runs so that every drawing of it points the same way, and stepping that passes over what a folded block hides. `src/project/executions.ts` reads `executions/<name>.json`: a trigger, starting store contents, an optional trace an agent wrote (always kept as `declared`), and optional expectations. `src/run/expect.ts` evaluates expectations against any trace.
2. **Done: the wired model is gone.** There are no wires, no `each`, no list of children and no generated composite code. A block's parts are the folders inside it. Every function's code is the agent's, and calls whichever other functions it needs directly. Contracts are optional. A `component` role covers groups of parts that are not called. The five old examples are replaced by `examples/tickets`.
3. **Done: executions on the canvas**, from traces an agent wrote, over `examples/messenger`.
4. **Done: the canvas rebuilt around the tree**, and looked at. After a first look the person asked for the architecture to be one top-down tree with the whole system on it, blocks small with their details in windows, an execution stepped through one arrow at a time, and a separate drawing of each execution from beginning to end. All of that is built, reviewed and seen; the person called it "absolutely fantastic".
5. **Done: what the agent is told.** There are no modes, every function block says where its code is, and one guide replaces two. Described in `PROJECT.md` under "Where the code is, and what Fragmentor does with it".
6. **Decided against: saving a trace from a test run.** A saved test stays what it is — values in, values out — and nothing records a trace from running one. What is left of the phase after it is the question below.
7. **Decided: a watched run stays what it is.** A run from the test bench lights up the blocks it reaches, on a bar of its own, and does not become a recorded execution; the person chose this on 2026-10-06.
8. **Done: documentation and a simplification pass**, after the six features. Breakpoints over traces are not built, and none of the six features includes them.

## Working

- **The website.** `site/` is a one-page static site in the window's own look: a canvas that draws `examples/tickets` block for block and steps its real "Book seats" execution in the agent's words, the two example exports embedded live under a click-to-use cover, and a Download button. Nothing in it is a framework or a build; `npm run site:demos` remakes the two exports. The button points at the repository's zip on GitHub, which only works once the repository is public or a release exists, neither of which is decided.
- **Where the code is.** Every function block that is not planned says where its implementation lives with `code`, a file relative to the project and optionally `#` and the name of the function in it. Nothing about where a block's folder sits says anything about where its code sits. `fragmentor check` reports a pointer that leads nowhere as a warning, because it cannot tell code nobody has written yet from code that moved, and whoever is working on it can.
- **What Fragmentor holds to a contract.** A function block whose ports are types, in a language there is a pack for, gets a contract, in its own folder in TypeScript and under `blocks/_contracts/` in Python; code that imports that contract is typechecked against it, run and tested; anything else is drawn. Per block, so one codebase can be part described and part built. The check lists what it is drawing rather than checking, and why. In TypeScript the contract is `contract.d.ts`, types only, imported with `import type`: a declaration file changes neither the codebase's rootDir nor its output and needs no package, so a rebuild leaves the buyer's own build exactly as it was (shown on json-server). A generated `contract.ts` from before is replaced at the next check. Existing code is held to its contract, when the person asks, through a small adapter beside it; where its file cannot follow the import rules, the agent says so rather than change the code.
- **The first minutes in the window.** Until the agent's first block arrives, the canvas shows a card, "Waiting for your agent", with the same two headed steps as the first-steps window and a Copy button beside the phrase to send. **Open Project…** on a folder that is not a project offers the new-project questions for that folder, with the starting point preset and **Start project**; on a folder inside a project it opens that project. When an AGENTS.md or CLAUDE.md was already there, **Add the line** adds the one line pointing at FRAGMENTOR.md, only on a click. When the `fragmentor` command is not installed, the first-steps window says so first, under "Before you start". A drawn function block with typed ports offers **Hold to its contract**, which leaves the agent a note asking for exactly that.
- **`fragmentor test` records executions.** Each execution whose trigger leads to code held to its contract is run in the sandbox and held to what ran: MET, or FAILED naming the step the run contradicts, with a count of what this run could not see. Anything else is held to its own expectations, and says it was not recorded and why.
- **Record in the window.** The bar above the drawing records the picked execution where its code is held to its contract: the run lights blocks and stores as it plays, then the **Written down | Recorded** toggle reads either trace, stepped on the tree or laid out as a Flow. A recorded step's page says what really happened, a written step's page says whether the recording saw it, and the bar's pill reads "Agrees with the recording, where it could see" or names, in red, how many steps were not seen; from one of those, "Leave a note on this step" opens with the finding filled in. A recording is dropped when the execution's trigger or starting rows change, and nothing is saved to disk. Where recording is impossible, Record is disabled with the reason beside it.
- **Rules, made by clicking.** With exactly two blocks selected, the panel offers **Add a rule…**: "X must never reach Y" or "only X may reach Y", with an optional reason, auto-oriented when only one way round could be a rule. Rules are sentences in `.fragmentor/rules.json`, kept in the project and shared; the project panel lists them, says which are kept and which broken, and removes one only after asking. A broken rule is an error with Flag where the evidence is exact, a warning, amber and worded as a guess that stops nothing, where Fragmentor had to count a whole file or a planned block is involved, and an error on the rules file itself when a rule names a block that is gone — telling the agent to re-point it or leave a note, which is the one edit the agent may make there.
- **Exporting a page.** `app/exportPage.ts` copies a fresh snapshot through the field inventory in `src/project/snapshotFields.ts`, whose types make every field, down to each trace step, either kept or replaced before it compiles; takes the project's folder and the home folder out of every string however a path spells them, and keeps only the file of a code pointer leading outside the project; and builds the page from the window's own markup and styles with one script bundled from the window's reading modules (`app/renderer/viewer.ts`), under a policy admitting only that script and those styles by their hashes. The finished page is searched for either folder and refused if one remains. The build fails if the bundle takes in anything that talks to the application. The page's legend is read-only and its bar offers no Record.
- **The Changes bar.** `app/renderer/changes.ts` reads what changed since the person last pressed **Mark as seen** (in memory within a session, from the marked commit after a restart) or since the last commit, through the kernel differ. The bar hides while the waiting card or first steps show, when git is missing, and when nothing changed; dots mark changed blocks only while the list is open, gathered onto folded parents the way note counts are; a removed block's **See it as it was** opens its old interface read-only.
- **What `fragmentor check` accepts from existing code.** A method as `file#Class.method` (drawn, never run, since it cannot be called with a value and `caps`); a file alone where no named function makes a step; the standard globals `URL`, `URLSearchParams`, `TextEncoder`, `TextDecoder`, `structuredClone` and `AbortController` in block code. A `stores` key in `cases.json` that is not a store entry is an error naming the one meant. `fragmentor rebuild` and the other phrases typed into a shell explain that they are for the agent.
- **Recording an execution, in the kernel.** `src/run/record.ts` runs the function an execution's trigger leads to, through the bench's own machinery, with every store read, write, remove and send reported by the harness; `src/model/recorded.ts` turns that into a trace marked `recorded` and checks each written-down step and expectation against it — seen, not seen with the reason, or not checkable from this run with the reason. On `examples/tickets` all four executions record and agree, and a wrong written step is caught. Only code held to its contract is recorded.
- **Undeclared reach.** Every snapshot reads, through `src/lang/typescriptReach.ts` and `src/project/reach.ts`, which blocks each block's TypeScript code directly reaches, following barrels and path aliases. A crossing into a service, external, database, storage, structure, queue or client, which no access on the block, inside it or above it names, is a warning with Flag, naming the file and function it goes through. What could not be followed is a dim "Not checked in the code" line under Reaches and a "Reach not checked" section in the check; where it is unsure, it does not warn. Messenger's Deliver Notification declares `writes client`. On the trial rebuilds: json-server's command calls `createApp` without saying it reaches the API, and realworld's seed script calls the article and user services in-process without saying so — both true. A redraw takes about 10–30 ms longer warm.
- **The project as it was, and what changed.** `projectAt` reads a whole project as it stood at any commit, from git; `src/project/changes.ts` says what changed between two points — blocks new, removed, moved (a block deleted and one pointing at the same code is called a move, with the evidence), built, re-pointed, their contracts, what they reach, their exposed entries and executions. `fragmentor diff` prints it for the agent. `src/project/snapshotFields.ts` classifies every snapshot field for the diff and for the export, so a new field cannot be added unclassified.
- **Architecture as containment.** A block's parts are the block folders inside its own; a `children` or `wires` field is refused with a message saying why. A block has a `role`: `function` is code that is called; `component` is a group of parts that is not (a module, a package, the infrastructure); `service`, `external`, `database`, `storage`, `structure`, `queue` and `client` are the things the code talks to. A `subtype` says what it is exactly, in free text. A non-function block has no ports, no capabilities and no code; it offers `exposes` entries — a table with its schema, a channel with its message, an operation with what it accepts and returns — and an operation may say which function inside answers it.
- **Dependencies.** Any block says what it reaches with `access` — `"reads app-db.users"`, `"shorten calls api.createLink"` — found among the block's own parts first, then beside it and above it, or by a path such as `infrastructure/app-db.users`. An access is drawn as an arrow from the block that reaches to the block it reaches, labelled with what it does, and gathered onto whatever is showing when one of them is folded away; coloured by block, an arrow that reads takes the colour of what it reads. **Dependencies: shown / hidden** below the drawing is how they are asked for; they start hidden, because the tree's own lines mean containment and an arrow is a different question.
- **The architecture as one tree.** Every block of every system is on screen at once, each under the block it is part of, joined by plain right-angled lines with no arrowheads: containment, and nothing else. Parts with no parts of their own are listed down the side of what they belong to, which is what keeps a system readable on one screen. A block with parts folds them away and brings them back, and folding is the only thing that takes a block off the drawing. There are no levels, and nothing is laid out by hand: `layout.json`, dragging and **Re-layout** are gone.
- **A block's windows.** A block on the tree is a small box — its name, its kind, its colour. Two buttons on it open the rest: **its interface** (a function's ports, a database's tables, a service's operations, and what it reaches) and **its code** (the whole file, coloured, with the function it stands for marked). The same two buttons are in the inspector. The inspector offers to edit the code Fragmentor holds to a contract, beside the contract holding it, and shows anything else read-only with the reason underneath.
- **One panel for every kind of block.** Whatever a block is, the inspector says the same things about it in the same order: its **Interface** — what the rest of the system uses it through, which is a function's inputs, outputs and capabilities and a database's tables, a queue's channels, a service's operations — what it **Reaches**, where its **Code** is, how to **Run** it, and last its **Versions**. The word for the kind of entry sits inside the interface rather than becoming a heading of its own, so reading one block's panel teaches you the next one's. Where an entry leads is written on that entry's own row. Shapes are coloured token by token rather than set in one flat green.
- **Executions, written down and held to what they say.** An execution `fragmentor test` cannot record is held to its own expectations, evaluated against the trace in the same file. That catches a file that contradicts itself and cannot catch one that is wrong about the code, since both halves are the agent's reading of it, and the guide and the report both say so. `examples/tickets` has four: booking seats, a booking turned away, cancelling one, and cancelling when the event is gone — one world, in which the booking the first makes is the booking the third gives back.
- **Executions on the tree.** `executions/<name>.json` files are read into the project, and their problems listed like any other. The bar above the drawing picks one and steps through it: **Restart**, **Step**, **Step into** and **Play**, with the step in words underneath. One arrow at a time is drawn, between the two blocks that step really joins, and it runs the way the step does, so an answer coming back points at whoever asked rather than back along the call it answers; a step that carried something flows, one that only set something off lights up; what a run left behind is a chip at the block responsible. The arrow goes over the blocks rather than under them, with its word put wherever there is room to read it, and where two blocks leave no room between them it goes round the outside of both. A step inside a folded block is passed over by **Step**, and **Step into** unfolds what hides it. A trace an agent wrote is labelled `declared`.
- **An execution as its own drawing.** **Flow** lays one execution out from beginning to end: step after step, left to right, wrapping onto the next row, with a block drawn again each time the run comes back to it, so nothing ever loops backwards. The step showing is marked on both drawings, and clicking any step in either opens its page.
- **A step's own page.** In the inspector: what the step is in the agent's words, the blocks it joins, what it carried, and the function that makes it, which opens in the code window.
- **Functions.** A function may take inputs and return outputs, or neither: one that returns nothing is typed `void` and is held to no result. Its code calls other functions by importing them from wherever they sit in the system, passing a value and its own `caps`; the typechecker holds the call to the callee's contract and capabilities. `fragmentor check` refuses imports of anything else but types and installed packages, and Node's built-in modules.
- **Reaching a store, and running from the top.** A `Store` port is a way into one table, file or structure and a `Queue` port into one channel; the access naming the port says which. The port is typed by what the entry holds. The bench offers somewhere to put rows before a run and shows what the run left — rows written, messages sent — and a saved test carries its rows. An operation and the function answering it have the same shape, except that a function needing nothing from the request may take no inputs. A client's action whose route ends at code has a bench of its own, so pressing the button runs what answers it.
- **The bench is a window of its own**, dragged wherever it is least in the way, with the architecture still readable behind it: the form, the rows a store starts with, what came back, the saved tests and the breakpoints are more than a panel beside the diagram can hold. It is pulled to whatever size the work wants by any of its edges or corners, rolled up to its title bar when the drawing underneath matters more, and lays the input, the result and the saved tests out side by side as soon as there is room, so there is little left to scroll. The inspector keeps one button to it, named the same thing the window is. It stays on the block it was opened for however the selection moves after that; where it was dragged to survives every redraw, and how big it was pulled outlives the session.
- **A block's versions: saved, and from git.** A version is a block and its parts — folders, saved tests, contracts in TypeScript, and the code they point at — as they stood at one moment. **Versions**, the last section of every block's panel, has two lists. **Saved** holds the versions the person chose to keep: **Save this version** takes a name and a description and writes the block as it is now to `.fragmentor/versions/`, which is committed with the project, so everyone working on it sees them; a saved version's name and description can be edited, and it can be deleted, after a second press. **Git history** holds every commit of whatever repository holds the project that changed the block, its parts or the code they point at, from the commit that added its `block.json`, the newest five until **Show all** is pressed. Which version the block is on is marked: a version is **in use** when the block is exactly as it — the latest commit, the version a swap put in place, or a saved version — and its row is highlighted; when the block is exactly as none of those, the one it was taken from is marked **changed since**. The same is said in a badge in the panel's header, so it is seen without scrolling. The section keeps a comparison on screen while the agent writes files and the person looks at other blocks. **Compare** runs every saved test of the block and its parts, from either version, against it as it is and as it was, and every other saved test in its system, and lists what comes out differently; it works in copies and changes nothing. **Swap to this** puts the block and its parts back as they were at that commit — folders, saved tests, contracts in TypeScript, and the code they point at — and refuses when that code is shared with a function outside it, naming the block to swap instead, or when it would go through a link. **Undo swap** puts back exactly what the swap replaced, kept in `.fragmentor/swaps/`, which git ignores; a swap or undo that stops part-way leaves Undo swap on offer, and nothing else is swapped until it is. New project starts a git repository when the folder is in none, and `FRAGMENTOR.md` asks the agent to commit each block it finishes.
- **Notes on blocks, between the person and the agent.** A note is a short conversation on one block, a file of its own under `.fragmentor/notes/`, committed with the project and never part of a block's versions. The person leaves one from **Notes**, the first section of every block's panel, and replies, resolves or deletes (after a second press) there; a run or a saved test that went wrong in the bench offers **Flag it**, which leaves a note carrying its input, stores, what was expected, what came back, what went wrong and what it logged; a test the agent has answered for that still fails offers **Flag it again**, on the same note. Whose turn it is follows from who wrote last: an open note is **for your agent** or **for you**, and only the person resolves. A block with open notes carries a count on its corner, amber while any waits for the person, gathered onto a folded block from its parts; a bar above the drawing says how many are with the agent and the words to tell it, **`fragmentor notes`**, with **Copy**, and how many are back, with **Show**; the project's panel lists every open note and what to tell the agent, and is where a note on a block that has gone is replied to or deleted. For the agent, `fragmentor notes [block-path]` lists what waits for it with each block's `block.json`, the file and line of its code and its tests; `fragmentor reply <id> <text>` answers; `fragmentor note <block-path> <text>` leaves one; `fragmentor check` says how many are waiting. The guide teaches the phrase, and a note left from the window brings an older project's guide up to date first. The watcher follows `.fragmentor/notes/` so an answer appears while the person watches, and the panel keeps what is being typed, and where, while the agent's changes redraw it.
- **Notes, narrower and followed up.** A note can be on some lines of a block's code, picked out in its code window, or on one step of an execution, from the step's page; each keeps what it pointed at as it was, and its **Show** opens the lines where they are now (found by what they said) or goes to the step. A problem Fragmentor reports on a block has **Flag** beside it. The agent runs `fragmentor working <id>` as it starts on a note, and the block's count pulses until it answers. `fragmentor reply` records the commit holding the work, when one was made since the person wrote that changed the block, and `--no-commit` records none, for a question; the answer then offers **Compare with before** and **Swap back to before**, which run the Versions section's own comparison and swap on the version before that commit. Once the agent answers a note flagging a run, the run is run again, as it was flagged and without touching saved tests, and again whenever the block's code changes; still wrong, it offers **Tell your agent**, which sends the new run back. A run that went wrong in the block itself carries a red flag on its corner instead of the word "failed" beside its kind, and failed blocks are outlined and glow red; a block with a note still with the agent that flags a run or a problem is drawn the same way, flag, outline and glow, however it is picked out or pointed at. In the note, such a message leads with **ERROR:** and the test or run in red, and **View failed test** unfolds what was run, what came back and why, with **Retry test**.
- **Commands for the agent.** `src/codegen/commands.ts` is the one list of phrases the person types to their agent: `fragmentor notes`, `review` (check the diagram against the code and leave notes, changing nothing), `rebuild` (redraw the diagram from the code), `explain`, `plan` (draw a change as planned blocks), `build`, `make` (design and build what is described straight away, with no plan to agree) and `cover` (add the tests a block is missing), most naming a block to mean that block and its parts. **Commands**, on a toolbar that holds nothing else but the two panel switches, and View › **Commands** open a window listing them, with the block picked out filled in; the guide's **Commands** section and, for Claude Code, a `/fragmentor-<name>` skill each under `.claude/skills/` are made from the same list, the skills written by `fragmentor check` and marked so the agent never runs one by itself. Opening the window, or leaving a note, brings an older project's guide and skills up to date.
- **`examples/messenger`**, a chat application described as it stands, none of whose code imports a contract, so all of it is drawn: a client with its UI and state, an API with a router and `auth` and `messaging` components, workers, and infrastructure holding a PostgreSQL database and a queue, pointing at real TypeScript under `src/`. Five executions are written down (sending a message, logging in, logging out, delivering a notification off the queue, and a scheduled clean-up), each step saying what it is and which function makes it, each with expectations its own trace meets.
- **`examples/tickets`.** A box office, a REST API, a PostgreSQL database, an outbox queue and a planned reminders job, with its code under `src/booking/` and each block pointing at it. Inside the API, `book-seats` and `cancel-booking` both use `find-event`, which therefore sits beside them; a `pricing` component holds `price-seat` and `refund-for`; `reserve` is used only by `book-seats` and sits inside it. Booking turns a request away early when it cannot be met, prices each seat at once, writes two tables and sends a confirmation. Thirteen tests pass.
- **A mark in every block's corner** saying what kind of thing it is, in the block's own colour: angle brackets for a function, a frame holding boxes for a component, a cylinder for a database, a person for a client.
- **Colour and arrangement.** Dashed means not built yet and nothing else. **By block**, the default, gives every block a colour of its own; **by kind** uses the vocabulary, in which hue says which world a thing belongs to, from most yours to least, with a legend that lists every kind, marks the ones on screen, and folds away. A kind's colour is changed from the legend and one block's from the inspector, remembered in the browser profile. A block's parts are drawn in the order of their folder names; nothing orders them by role, and no block can be dragged.
- **A question tree when a project is created**, asking where you are starting from, whether to plan first, how finely to divide the work and optionally the language, and writing the answers into `fragmentor.json`. `fragmentor init` does the same for an agent. Once the project exists, a window says what to send the agent first, from those answers as written — `fragmentor rebuild` for code already there, `fragmentor plan <what you want to build>` to plan first and `fragmentor make <what you want to build>` to build straight away — with the folder to open it in, every other command, and where to find them again. The empty canvas says the same until the agent defines a system.
- **The application menu.** **New Project…**, **Open Project…**, **Close Project** and **Export…** are under File; View › **Commands** opens the commands for the agent, and View › **Reload Project** (Ctrl+R) reads the project from disk again, in place of reloading the page, which would drop back to the start screen. There is no **Generate code**: the agent's `fragmentor check` rewrites the contracts, the guide and the slash commands every time it runs, and nothing in the window needs the contracts current, since running and testing strip them.
- **Planned architecture.** A block with `"planned": true` is drawn greyed out with a dashed edge and a `PLANNED` label, its types may be words, nothing about it is an error, and nothing is generated, checked or run for it. Planning spreads downward only. A contract Fragmentor wrote for a block that is now planned is taken away; no code is ever touched, because none of it is Fragmentor's.
- **Agent guide.** One `FRAGMENTOR.md`, written for the one project it sits in. It teaches containment (put a block inside another only when it is part of it, and a shared one inside the lowest block holding everything that uses it), where a block's code goes, contracts and testing where they apply, and executions. Its worked example is a component holding three functions, one calling the other two, with their code under `src/pricing/`, held by test to check and pass exactly as shown.
- **Language packs.** TypeScript and Python are both generated, typechecked, run and tested. A Python contract is TypedDicts and a Protocol under `blocks/_contracts/<path with - as _>/contract.py`, because Python cannot import through a hyphen; code binds by importing its contract's dotted module under `if TYPE_CHECKING:`, with `from __future__ import annotations` first. `fragmentor check` runs an `ast` pass with the project's interpreter — a top-level undecorated `async def` annotated from its contract, contracts imported for types only, a compute-only standard library plus `asyncio`, no `open`, `print` or `input`, local imports only of bound blocks' files, nothing shadowed, no `__init__.py` holding code, no `# pyright:` comment — then bundled pyright, from a config written outside the project. `harness.py` speaks the TypeScript harness's protocol as JSON lines, with stdin and stdout both taken away from the block's own code.
- **Running, watching and pausing.** A function runs in a separate process against given values, with substitutes for its capabilities, checked against its contract. Every call the run makes, anywhere in the system, is recorded with the call that made it, and played back on whatever diagram is on screen: a block lights up when it, or anything inside it, is running, and says how its own calls went or, for a group of parts, how many ran inside it. A breakpoint pauses a run before a function; **Continue**, **Step**, **Continue all** and **Stop** steer it. Tests live in `cases.json` beside each function.
- **Desktop application.** Draws the diagram and redraws it as the agent works, keeping the view and selection; lists problems against their blocks; shows a banner over the last good diagram when a file is half written; warns about unsaved edits when the file changes underneath. The code of a block held to a contract can be edited, in the file the block points at; contracts and code Fragmentor only draws are read-only. Double-clicking a block folds or unfolds its parts, or opens its code when it has none; blocks the agent adds are brought in one after another.
- **The trace kernel**, described under "Current focus", with its tests. The tree and the Flow draw with it, and Record's traces, marked `recorded`, are made with it.
- **The application checks itself.** `npm run check:app` plays an agent against throwaway copies of `examples/tickets` and `examples/messenger`, and projects it makes for itself, driving the features above through the real window, Record, rules, the Changes bar and Export included; `selfCheckFailures` in `app/main.ts` lists what it holds the window to. Where Python 3.11 is installed, the guide's Python example is run from the bench, paused, stepped and tested. Anything the window logs as an error fails the check.

## Known problems or uncertainties

- **Only Claude agents have followed the guide**: two rounds of trials, the person's own Claude Code rebuild of json-server, and two agents following it in Python. No Codex agent has.
- **A block written in words gets no contract**, which is right, but an agent that writes `Order[]` in a project it is meant to be building gets only a line in the check's report. Whether that deserves more is unsettled.
- **A wide system does not fit on screen at a readable size.** It opens at 60%, the size the person chose, at the top of its first system, with the rest a drag away; **Fit** still shows all of it, as small as it has to be. On a rebuilt realworld API the largest branch starts off the left edge. Folding a part now narrows its row.
- **The flow view wraps every five steps**, whatever the width of the window.
- **A dependency arrow can pass behind a block.** Arrows are arcs between two boxes and nothing routes them around whatever stands between; they can be hidden altogether.
- **A declared trace is only as true as the agent's reading of the code** where that code is only drawn: nothing runs to check it, and its expectations are the same reading again, so holding one to the other catches a contradiction rather than a mistake. Where the code is held to its contract, Record and `fragmentor test` hold what the run could see to it.
- **An expectation cannot say that something did not happen in a part the run did touch.** `never` names a part in which nothing at all may happen, so "the seats were never put back" — a write that did not happen to a table the same run read — is not sayable. It is the one thing `examples/tickets`'s fourth execution exists to show and the one thing it cannot assert.
- **A function passing capabilities on declares them.** `book-seats` binds the stores `reserve` writes, because it hands `reserve` its own `caps`, so its access list reads as though it wrote them itself.
- **A callee uses its caller's store.** A port bound to one store in the caller and to another under the same name in a function it calls would reach the caller's. Nothing checks for that.
- **A role is the agent's to write**, as `planned` is. There is no control in the application for either.
- **A store's substitute is a dictionary, not a database**: `read`, `list`, `write`, `remove`, and no queries, ordering, transactions or constraints. A `Queue` only sends.
- **An exposed type that will not parse is kept as words**, so a typo in a schema is shown rather than reported.
- **Running an entry runs the code, not the hop to it.** The route from a client to a service is shown on the panel, not animated.
- **Packages can reach the outside world** without a capability. Only Node's built-in modules are refused.
- **Reach is read one call deep, in-process, in TypeScript only.** Packages, network calls, dynamic `import()` and `require` are listed as not checked, and so is a block pointing at a class method, whose whole file is then counted; json-server's rebuild has ten such lines. When one file holds the code of parts in different branches, its other top-level code is counted as their common parent's, which is never warned on. Python is held to its declared access alone.
- **A block's code is found by name, not by parsing.** Whether its code imports its contract, and whether the file really declares the function rather than only mentioning it, are decided by scanning the text. A file that imports its contract and never uses the types it imported counts as held to it, and only the run-time check on its inputs and outputs then holds it to anything.
- **A block Fragmentor runs can only call other blocks it runs**, because the compiled copy holds those files and nothing else. That is honest but narrow, and it is what stops a half-converted codebase being run.
- **A file may hold several blocks, with two costs.** Editing it from the window saves the whole file, so unsaved edits made through one block can overwrite those made through another until the redraw warns about it; and binding one of its functions holds the whole file to Fragmentor's import rules, which the guide says but the file itself does not.
- **Watching has limits.** A run records its first 2000 calls, and a value larger than about 200 KB is described rather than shown. Breakpoints are not saved with the project.
- **Held calls take turns.** Several calls held at once are let go one at a time by Continue, all together by Continue all. Step goes into the call it lets go.
- **Declared traces guess what caused each step** when the agent does not say. After a callback into the caller the list is genuinely ambiguous; the guess is documented, and a step can name its cause.
- **Code colouring is scanned, not parsed.** Nothing depends on the colours being right.
- **The animations are checked for happening, not for how they look.**
- **The `fragmentor` command needs `npm link` once.** The guide tells the agent to ask for it.
- **A self-check cut off mid-run can leave the Windows clipboard wedged machine-wide** (it saves and restores the person's clipboard around the copy step). Signing out or rebooting clears it; until then only the check's own copy step can fail, and everything else stands.
- **Two self-checks must never run at once.** They share the system clipboard and window focus, so each can fail the other, and several at once with test suites beside them have brought this machine down.
- **An exported page is a snapshot**, of the project as it was and of the executions as written down; nothing on it is ever recorded. It is checked in Chromium by the self-check; Edge and Firefox wait for the person's look, Safari is untested, and phones are not in view. Block names are cut to fit as Segoe UI sets them. Free text the agent wrote has the project's folder and the home folder taken out, not every other path it may mention; a project folder of one name on a disk with no drive letters, such as `/srv`, is not looked for, since it names nobody.
- **A redraw takes the cursor out of the code editor**, keeping the unsaved text.
- **An edit conflict is warned about, not prevented.**
- **Reading the clock or randomness directly is not detected.** In Python, `time`, `random` and `uuid` are allowed imports for the same reason.
- **The Python rules are honesty checks, not a sandbox.** Allowed modules such as `asyncio`, and installed packages, can still reach processes and the network, exactly as TypeScript's packages can.
- **A Python block function with free variables, or a file shadowed by an installed name, fails loudly** rather than being watched wrongly. `-I` hides `pip --user` packages, so a project that needs packages needs a `.venv`. The interpreter search is `.venv` then PATH, untested on macOS and Linux GUI launches.
- **A value holding NaN or Infinity is refused by the Python harness** — a store write raises and a result reports the reason — where the TypeScript harness quietly records `null`.
- **The port type language has no recursion.**
- **A block cannot appear twice in one parent**, because a block is its folder.
- **A swap regenerates nothing.** A version brings its own contracts in TypeScript only; a Python contract lives in `blocks/_contracts/`, outside the block's folder, and the next `fragmentor check` rewrites it. Anything generated elsewhere that depends on the block likewise stays as it was until that check. That is what lets Undo swap put things back exactly.
- **A swap can break code outside the block** that imports it, because what a block uses beside it is not part of its version. Compare shows it; nothing prevents it.
- **A saved version is kept under its block's path.** A block moved or renamed leaves its saved versions behind, shown in no panel, as its git history starts again at the move.
- **Only three kinds of version are checked for being in use**: the latest commit, the one a swap put in place, and the saved versions. A block put back by hand to match an older commit is shown as changed since the latest one.
- **Swapping to a saved version leaves alone code it knows nothing about.** A file under code the block has pointed at only since it was saved stays as it is, because the version cannot say whether it was there then; so the code of a part added since can be left behind with nothing pointing at it. A commit knows every path, and a swap to one takes such a file away.
- **A repository that ignores `.fragmentor/` keeps saved versions from being shared.** Saving still works, and says which rule is keeping it on this computer.
- **Only the latest swap can be undone**, from Versions in its block's panel. An undo after the agent has changed those files puts back the files from before the swap; what the agent wrote is kept in `.fragmentor/swaps/`, where nothing in the application reaches it.
- **A swap across a rename that changed only a name's capitals is refused on Windows and macOS**, whose disks do not tell such names apart, as is one where the disk and git spell a name with different capitals.
- **A block's history starts again when its folder moves**, and a commit to a file several blocks share is listed as a version of each of them.
- **Versions need the project to load.** While it cannot be read, the window cannot list them, or undo a swap.
- **Compare's older side reads today's copy of any file its version did not hold**, through the FileSystem capability, since the copy it runs in holds only the blocks and their code.
- **The list of versions is read again when the window regains focus or the project changes**, not the moment a commit is made.
- **A note is on a block's path.** A block moved or renamed leaves its notes pointing at nothing until the agent changes `block` in each; the check warns about every open one, and the window lists it in the project's panel, where it can be replied to or deleted.
- **The commands work only where the agent reads the guide**: Claude Code through `CLAUDE.md` and its slash commands, Codex through `AGENTS.md`. A project whose guide predates them learns them at its next `fragmentor check`, or when a note is left from the window.
- **A run is flagged on the block it was run from.** A block deeper in the run that really threw is shown in Watching, and is not offered.
- **Which commit an answer records is worked out, not told.** It is the latest commit, if it was made since the person wrote and changed the block; an answer to a question on a block the agent has just committed other work on records that work unless the agent says `--no-commit`.
- **A flagged run is run again only while its block's panel is open**, and only when the block's own code or its parts' has changed: a change to something it calls from outside it is not noticed until **Run it again**.
- **A run too large to keep whole is not run again.** Its note says so; the agent still reads what was kept.
- **Notes on lines follow the lines by what they said.** Once the agent has changed them, **Show** marks where they were and says so.
